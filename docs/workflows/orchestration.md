# Orchestration

여러 AI 에이전트에게 작업을 나눠 맡길 때의 절차다. Orca를 오케스트레이터로 쓰는 경우를 기준으로 한다.

오케스트레이터는 작업을 직접 다 하지 않는다. 작업을 쪼개고, 하위 작업마다 가장 맞는 에이전트를 배정하고, 결과를 검증해서 합친다.
모든 배정에는 이유를 한 줄 이상 남긴다. 이유 없는 배정은 하지 않는다.

## 1. 작업 분해

요청을 받으면 먼저 하위 작업으로 나누고, 각 하위 작업마다 아래를 정리한다.

- 목표: 끝났을 때 무엇이 달라져 있어야 하는지
- 범위: 건드릴 파일·모듈 (겹치면 병렬로 돌리지 않는다)
- 유형: 아래 라우팅 표의 유형 중 하나
- 완료 기준: 어떤 테스트나 확인을 통과하면 끝인지

## 2. 라우팅 기준

기본값이며, 결과를 보고 조정한다.

| 작업 유형 | 기본 에이전트 | 이유 |
| --- | --- | --- |
| 설계, 여러 파일에 걸친 리팩터링, 원인이 불분명한 버그 | Claude Code | 맥락을 넓게 추론하고 변경 계획을 세우는 일이 중심이라서 |
| 범위가 명확한 구현, 테스트 작성, 단일 버그 수정 | Codex | 요구사항이 정해져 있어 빠르게 실행만 하면 되는 일이라서 |
| 큰 코드베이스나 긴 문서를 읽고 요약·조사 | Gemini | 한 번에 넣어야 할 컨텍스트가 커서 |
| 코드 리뷰 | 작성자와 **다른** 에이전트 | 자기가 쓴 코드를 자기가 채점하지 않게 하려고 |
| 단순 반복 작업 (rename, 포맷, 의존성 버전 올리기) | 가장 가볍고 싼 에이전트 | 추론이 필요 없어서 비싼 모델을 쓰는 게 낭비라서 |

- 표에 없는 유형이면 그 작업에서 가장 중요한 능력(추론 / 실행 속도 / 컨텍스트 크기 / 비용)을 먼저 적고, 그 능력이 가장 강한 에이전트를 고른다
- 배정할 에이전트가 설치되어 있지 않으면 표의 다음 후보로 바꾸고 그 이유를 보고 표에 적는다

## 3. 병렬과 순차

- 병렬: 범위(파일)가 겹치지 않고 서로의 결과를 기다리지 않는 작업만. 각 작업은 별도 worktree에서 돌린다
- 순차: A의 결과(인터페이스, 스키마, API 계약 등)를 B가 써야 하면 A를 먼저 끝내고 그 결과를 B의 프롬프트에 넣는다
- 같은 파일을 두 에이전트에게 동시에 주지 않는다. merge 충돌은 사람이 직접 풀어야 하기 때문이다

## 4. 에이전트에게 넘기는 프롬프트

전체 대화를 넘기지 않고 아래만 준다.

- 목표 / 범위(수정해도 되는 파일, 건드리면 안 되는 파일) / 완료 기준
- 필요한 선행 결과 (있으면)
- "범위 밖 수정이 필요하면 멈추고 보고할 것"

## 5. 검증과 통합

- 각 결과는 완료 기준(테스트, 빌드)을 실제로 돌려서 확인한다. "끝났다"는 에이전트의 보고만 믿지 않는다
- 중요한 변경(인증, DB 마이그레이션, 동시성, 결제)은 작성자가 아닌 에이전트에게 리뷰를 맡긴다
- 같은 작업이 두 번 실패하면 같은 에이전트에게 세 번째로 맡기지 않는다. 다른 에이전트로 바꾸거나, 작업을 더 잘게 쪼개거나, 사람에게 묻는다
- 에이전트가 권한·신뢰 확인(훅 신뢰, 샌드박스 밖 실행 등)에서 멈추면 오케스트레이터가 대신 고르지 않고 사람에게 묻는다
