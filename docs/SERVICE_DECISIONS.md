# 서비스 결정 — 2026-09-14

## 식당 정보 출처와 저장 범위

- 확장 서비스는 현재 위치로 외부 Places API를 조회한다. 전국 식당을 미리 우리 DB에 저장하지 않는다.
- 혜화 DB는 전시를 위한 임시 데이터 공급 수단이며, 확장 서비스의 검색 대상을 제한하지 않는다.
- 우리 DB에는 사용자 리뷰·Pick·좋아요 등 자체 데이터와 이를 연결할 외부 장소 식별자를 저장한다.
- 외부 식당은 제공사와 장소 ID로 식별한다. 사용자 활동이 없는 모든 검색 후보를 DB에 등록하지 않는다.
- 외부 응답의 영구 저장·캐싱은 제공사 정책을 따른다. 현재 Redis나 응답 캐시를 추가하지 않는다.
- DB 후보 조회와 외부 후보 조회는 분리하고, 추천 처리는 JPA Entity가 아닌 공통 후보 응답을 사용하도록 구현한다.

## 확장 서비스의 추천 흐름

1. 브라우저가 사용자 동의 아래 현재 좌표를 얻어 서버에 전달한다.
2. 서버가 음식 선택을 Google 지원 분류로 변환하고 Nearby Search (New)에 반경 5km와 함께 전달한다.
3. Google이 지원 조건과 자체 정렬 기준으로 선별한 후보를 최대 20개 반환한다.
4. 서버가 반환된 모든 후보의 평점·거리·동행 적합도 점수를 계산하고 정렬한다.
5. 정렬된 상위 최대 5개를 순서대로 제공한다. 1~4개는 그대로, 0개만 검색 결과 없음으로 처리한다.

- 5개를 먼저 자른 다음 순위를 매기지 않는다.
- 주변 전체 식당의 절대적인 TOP 5가 아니라 외부 검색 후보 중 추천 결과다.
- 동행 적합도는 후보 제외가 아닌 가산점이다. 미확인 속성 때문에 후보를 버리지 않는다.
- Google FieldMask는 반환 필드 선택이며 검색 조건이 아니다.
- API 오류·시간 초과는 정상 검색 결과 0개와 구분한다. 임의로 반경·음식 조건을 완화하지 않는다.
- Google 응답을 받았다고 해당 식당의 현실 상태가 실시간으로 보장되는 것은 아니다.
- Google 호출에 실패했다고 전시 DB로 조용히 대체하지 않는다. 데이터 공급 방식은 명시적으로 구분한다.

근거: [Nearby Search](https://developers.google.com/maps/documentation/places/web-service/nearby-search),
[Places 저장 정책](https://developers.google.com/maps/documentation/places/web-service/policies).

## 확정된 전시 범위

- 모바일 중심 웹앱. 검색은 사용자 현재 위치 기준 반경 5km 고정.
- 혜화 주변 식당은 팀이 직접 검수한 자료를 DB에 등록한다. 추천 결과를 코드에 고정하지 않는다.
- 전시 DB 방식에서는 등록 범위 밖의 결과가 없을 수 있다. 외부 API 검색 방식에는 이 제한을 적용하지 않는다.
- 후보 0개는 검색 결과 없음, 1~4개는 그대로 제공, 5개 이상은 상위 5개 제공.
- 후보 부족을 이유로 검색 반경이나 조건을 자동 완화하지 않는다.
- 기존 분위기 태그 8개와 자동 태그 추출은 폐기. 입력은 누구와 / 어디서 / 어떤 음식 중심.

## 동행 적합도

- 전시용 데이터는 팀이 직접 판단해 입력하며, 데이트·혼밥을 속성 조합으로 자동 추론하지 않는다.
- 적합도는 후보 제외 조건이 아닌 순위 가산점으로 사용한다.
- true는 적합 확인, false는 부적합 확인, NULL은 정보 없음으로 구분한다.
- false와 NULL에는 초기 가산점을 주지 않는다. 알 수 없는 값을 false로 채우지 않는다.
- 추론 전용 컬럼이나 자동 보정 로직은 지금 추가하지 않는다.
- Google 속성 매핑은 이번 수동 데이터 입력 경로에 포함하지 않는다. 향후 재검토 시 이용 조건과 출처를 확인한다.
- 데이트 / 친구 / 가족 / 혼밥 / 회식의 nullable boolean 5개 컬럼을 V2에 포함한다.
- 사용자 리뷰의 경험 카테고리는 별도 누적 데이터이며 현재 추천 입력과 구분한다.

## 미확정: 구현 전에 확인

1. 평점·거리 정규화 방식, 가중치, 동행 가산점 크기. 평점 비중이 거리보다 높다는 방향만 확정.
2. 평점의 출처·척도·미확인 값 처리와 동점 정렬 기준.
3. 식당 원본 자료, 좌표, 음식 분류 목록 및 사진·원문·출처 연결 방식.
4. Google 초기 후보 정렬 기준(POPULARITY / DISTANCE)과 요청할 정확한 FieldMask.
5. 실제 음식 선택지와 Google 지원 분류 매핑, 외부 동행 속성 매핑 기준.

## 다음 구현 순서

1. Google Cloud 프로젝트·Places API 키 준비. 키는 로컬 환경변수에 두고 저장소·채팅에 공유하지 않는다.
2. 소규모 Nearby Search 실험으로 응답 시간, 음식별 후보 수, 속성 누락률, 요청당 비용을 확인한다.
3. 외부 후보 조회 클라이언트와 공통 후보 DTO를 구현하고 가짜 응답으로 자동 테스트한다.
4. 점수 기준을 합의한 뒤 추천 정렬과 최대 5개 응답, Swagger 명세를 구현한다.

2026-09-15: Google 후보 조회 클라이언트와 모의 테스트를 구현했다. 실호출 검증·음식 분류 매핑·추천 점수 계산·HTTP API는 아직 남아 있다. 미정인 가중치를 임의로 기본값 처리하지 않는다.

## V2 구현 결정

- PostGIS geography(Point, 4326)와 GiST 공간 인덱스를 함께 추가한다.
- 위치는 기존 longitude / latitude에서 생성하는 저장형 생성 컬럼으로 동기화한다.
- 동행 값의 기본값은 두지 않는다. 기존 데이터도 미확인(NULL)을 유지한다.

자료가 제공되기 전 식당 데이터나 평점·적합도를 임의로 생성하지 않는다.
V1은 유지하고 합의된 변경만 V2 이후 마이그레이션으로 추가한다.
